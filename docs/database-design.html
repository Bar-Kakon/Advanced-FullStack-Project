How to read this document

A relational database is designed by normalising: find the entities, split them until nothing repeats, and let JOIN put them back together at read time. MongoDB has no joins worth planning around, so the design question flips: what gets read together, and how often does it change? Every decision on this page comes back to that one question.

The five questions

What we ask before every field

  1. Is it always read with its parent? Yes → lean embed.
  2. Does it grow without bound? Yes → must reference. A document is capped at 16 MB.
  3. Is it queried on its own? Yes → give it a collection so it can carry its own index.
  4. Is it shared by more than one parent? Yes → reference, or you get copies that drift.
  5. Does the relationship itself have attributes? Yes → it wants to be a document (that is exactly what memberships is).
The three shapes in this schema

Everything here is one of these

Embedded sub-document — lives inside its parent, has no _id you ever query by. Example: users.location, tasks.subTasks.
Reference — an ObjectId pointing at another collection, resolved with Mongoose .populate() or an aggregation $lookup. Example: tasks.assignee.
Junction collection — a document whose whole job is to connect two others and carry the attributes of that connection. Example: memberships, connections, ratings.
